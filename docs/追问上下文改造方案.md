# 追问上下文改造方案（轻量版）

> 状态：已实施（2026-11-26）；验收 `npm run check` / `npm run smoke` / `npm run test:ask-context` 全过
> 日期：2026-11-26
> 目标：把精读产物变成**可检索、可引用**的追问上下文，替代现在的「截前 3000 字 + 头尾拼正文」

---

## 1. 背景

### 1.1 网页 AI 阅读产品的共同做法

调研 NotebookLM / SciSpace / ScholarLens 及通用 agent 论文助手后，结论一致：**追问质量取决于上下文组装，不取决于模型是否带工具。**

| 路线 | 代表 | 做法 | 代价 |
| --- | --- | --- | --- |
| 长窗口直塞 | NotebookLM / Kimi | Source 解析 → Retrieval and Ranking → 长上下文组织 → 带内联引用作答 | token 贵、长文失焦 |
| 检索式 RAG | SciSpace / ScholarLens | 分块向量化，按问题取 top-k；选中片段即检索锚点 | 依赖切块与检索质量 |
| 结构化编译 | LLM Wiki | 原始资料不动，增量维护实体/主题/矛盾点，追问读笔记 | 需持续维护 |

三者都有的两个机制：**按问题选上下文**（不是全塞）、**回答带来源标记**。

### 1.2 本项目现状

链路：`public/app.js:984 ask()` → `POST /api/ask` → `server/index.mjs:350 handleAsk()` → `server/prompts.mjs:119 askMessages()` → `streamChat()` → SSE `delta` → `state.askThread` → `papers.ask_json`。

问题（代码级证据）：

1. `askMessages()` 中 `reading.slice(0, 3000)`：精读固定 7 节，前 3000 字通常只覆盖到「核心方法」，**「实验与结论」「局限与可延伸」「精读要点」基本被切掉**。
2. `trimPaper(paper, 12000)`：头 70% + 尾 30% 拼接，与问题无关；中间整段丢失。
3. `askMessages()` 不接收 `askThread`：**每一问都是独立请求**，"和 Transformer 比呢"这类指代无法理解。
4. `structure`（concepts / claims）只用于图解渲染，**完全没进追问上下文**；其中 `concepts[].terms` 是模型抽取的原文检索词，正是现成的检索键。
5. 回答无来源标记，用户无法核对结论出自哪一节。
6. 请求体每次都带完整 `paper.text` + 完整 `readingText`，长论文浪费带宽。

## 2. 目标与非目标

### 目标

- 精读的 7 节各自成卡，按当前问题**选 2–3 节**进上下文；
- 选中片段优先，且作为检索锚点；
- 带上最近两轮问答的压缩摘要，支持指代型追问；
- 上下文里每块带来源标记，模型被要求据此作答；
- 单次追问上下文**控制在约 6000 字符内**（现状约 19000 字符，且大量无关）。

### 联网增强（新增，默认开）

用户决策：追问区提供「联网增强」开关，**默认开**；关掉即回到纯论文模式。理由：服务商托管型联网工具（DeepSeek `deepseek_web_search`）由服务端完成检索与上下文拼接，客户端只声明一次 `tools`，不增加自建搜索/抓取链路；对"后续进展 / 外部验证 / 与其他工作对比"这类问题，网络信息能让回答更全面。

设计约束：

- **不自建 tool 循环**：只用服务商托管工具（响应里直接带引用与正文），客户端不解析 `tool_calls`、不做二次请求；
- **按 provider 能力注入**：只有声明支持的服务商才加 `tools`，其余保持纯论文模式并在界面明确提示，不静默降级；
- **来源可区分**：回答里 `[§…]` = 论文内、`[网络]` = 外部，SYSTEM 同步告知模型两类来源；
- **可关闭**：开关状态存 localStorage，关掉后请求体不含任何 `tools`。

详见 §5.3 / §6.1 / §6.2。

### 非目标（明确不做）

- 不自建搜索 API / 网页抓取 / function-calling 执行循环——联网只用服务商托管工具；
- 不引入 embedding、向量库或任何新依赖——保持零依赖；
- 不新增数据库列——`papers` 表结构不动；
- 不改 demo 模式的行为；
- 不做模型级 Query Rewriting（那会多一次 LLM 调用，属于"中间版"）。

## 3. 改造后数据流

```
精读完成 → state.readingText（完整 markdown，已落 papers.reading_md）
                    │
用户提问 ───────────┤
选中片段（可选） ────┤
最近 askThread ──────┤
structure（可选） ───┤
                    ▼
        POST /api/ask（body 增加 askThread / structure / webSearch）
                    ▼
  buildAskContext()  ← 新增纯函数模块 server/context.mjs
    ① 切 7 节摘要卡（运行时，不落库）
    ② tokenize + 打分 + 取 top-N 节 / top-N 原文段
    ③ 压缩历史问答（最近 3 轮，含指代检测）
    ④ 按预算组装带来源标记的上下文
                    ▼
  askMessages()（改为接收组装好的 contextBlock）
                    ▼
  webSearch=true → provider 支持？→ 注入服务商托管 tools
                    ▼
  streamChat() → SSE delta → 前端渲染（来源角标）→ askThread → ask_json
```

关键点：**摘要卡是运行时结构，不落库**。精读结果是唯一的真相，每次追问现切现用。这样不需要 schema 迁移、不需要精读完成后额外回写，也不会出现"卡片和精读不一致"。代价是每次请求多传一次 `reading`（现在本来就在传）。

## 4. 核心设计

### 4.1 章节摘要卡：`splitReadingCards(md)`

放在 `server/context.mjs`（新文件，纯函数，无副作用，便于单测）。

- 复用 `public/text.js:114 parseReading()` 的规则：按 `^#{1,4}\s+` 切，去掉「一、」前缀；
- 只保留 `READING_SECTIONS`（`server/prompts.mjs:8`）里的 7 个标题；
- 每节输出：

```js
{
  title: '核心方法',          // 来源标记用
  body:  '……',               // 去掉 markdown 列表符号后的正文，≤900 字符
  source: '§核心方法',
  tokens: ['方法', '输入', 'state', 'space', ...],  // 见 4.2
}
```

- 不做二次摘要：**不调模型**，直接取该节正文，超长时取前 900 字符。理由：精读本身就是摘要，再摘要会丢细节且多一次调用。

### 4.2 检索：中文 bigram + 词频打分

无分词依赖，纯字符串处理：

```js
function tokenize(text) {
  // 1. 小写化；英文/数字：/[a-z][a-z0-9-]{1,}/g
  // 2. 中文连续串：切 2-gram（"核心方法" → 核心/心方/方法），单字串保留单字
  // 3. 去停用词：的/了/和/是/在/有/这/那/什么/怎么/如何/为什么/吗/呢 ...
}
function scoreCard(card, queryTokens) {
  // token 命中：1 + min(count, 3) * 0.3
  // 标题命中：× 2
  // structure.concepts[].terms / claims 命中：× 1.5（原文检索词，信号强）
  // 除以 sqrt(body.length) 做长度归一，避免长节通吃
}
```

- query 来源：当前问题（权重 1）+ 选中片段（权重 3，若存在）；
- 取 `score > 0` 的前 3 节；若全部为 0（问题与论文无关），退化为「一句话结论 + 核心方法 + 精读要点」三节兜底；
- 正文段落：把 `paper.text` 按空行/换行切成段，过滤 < 40 字符的段，同样打分取 top-2，每段 ≤700 字符。若 `selection` 非空，优先取与 selection 字面重叠最多的段。

### 4.3 多轮与指代

前端 `ask()` 传 `askThread`（前端已有完整记录，只截取最近 6 条即 3 轮，每条 text ≤400 字符）。

服务端：

- 过滤 `error` 条目和 `'…' / '思考中…'` 占位（与 `public/report.js:41 qaPairs()` 同口径）；
- 压缩成一段文本：

```
最近对话：
用户：<问题1前 120 字> → AI：<回答1首句 80 字>
...
```

- 指代检测：当前问题命中 `/^(它|他|这|那|这个|那个|前者|后者|上面|上述|刚才)/` 或长度 ≤12 且含「呢/吗」，则把**上一轮问题**也并入 query tokens（权重 1.5）。这是启发式，不调模型。

### 4.4 上下文预算

| 块 | 上限（字符） |
| --- | --- |
| 论文标题 | 100 |
| 选中片段 | 1200（现为 4000，压缩） |
| 精读卡 top-3 | 2700（每节 900） |
| 正文段 top-2 | 1400（每段 700） |
| concepts / claims 摘要 | 600 |
| 最近对话摘要 | 400 |
| 问题 + system | 600 |
| **合计** | **约 6900** |

超出时按「正文段 → 历史摘要 → 选中片段」顺序裁剪；精读卡不裁（那是精读产物本身）。

### 4.5 来源标记

上下文里每块前置标记：

```
[§核心方法] ......
[原文段落 3] ......
[选中片段] ......
[概念] SSM：状态空间模型（terms: state space layer / SSM）
```

`askMessages()` 的 system 增加一句：**引用论文事实时在句末标注来源标记，如 `[§核心方法]`；引用网络信息时标注 `[网络]`；标记必须来自实际材料，不要编造。** 前端把两类标记渲染成不同样式的小角标（见 6.2）。

联网工具自带引用（如 DeepSeek 的 `web_search_call` / 引用标记），服务端**不解析**这些结构，只透传正文增量；模型按 system 要求具体标注时，引用会落在 `delta.text` 里，前端照常渲染。

## 5. 接口与数据结构变更

### 5.1 `POST /api/ask` 请求体

| 字段 | 现状 | 改造后 |
| --- | --- | --- |
| `paper` | 必传 | 必传（不变） |
| `question` | 必传 | 必传（不变） |
| `selection` | 必传（可空） | 必传（可空，权重提高） |
| `reading` | 必传 | 必传（不变） |
| `askThread` | 无 | **新增**：最近 6 条 `{role,text,quote,error?}` |
| `structure` | 无 | **新增**：`state.structure`，取 concepts / claims |
| `webSearch` | 无 | **新增**：布尔，追问区开关状态（默认 true） |

响应 SSE 帧不变：`delta` / `thinking` / `error` / `done`。来源标记写在正文文本里，不加新事件类型；联网工具产生的服务端事件（`web_search_call` 等）不转发给前端。

### 5.2 联网工具能力矩阵（服务端按 provider 注入）

| provider | 联网方式 | 请求参数 | 支持 |
| --- | --- | --- | --- |
| `deepseek` | 服务商托管工具，服务端检索+拼接 | `tools: [{type:'deepseek_web_search'}, {type:'deepseek_read_url'}]` | ✅ `deepseek-flash` / `deepseek-v4-flash` / `deepseek-v4-pro`（2026-11-13 起） |
| `openai` | Chat Completions 仅特化模型 | 需 `gpt-5-search-api` + `tools:[{type:'web_search'}]` | ⚠️ 仅当当前模型是该特化名；否则提示不支持 |
| `kimi` | Chat 内置 `$web_search` 已于 2026-10-20 退役，仅 Responses / 独立 API 可用 | — | ❌ 当前 Chat Completions 接入不支持 |
| `zhipu` | Chat Completions 工具或独立 Web Search API | 私有参数 | ❌ 本轮不接（协议与 OpenAI 不通用） |
| `ollama` / `custom` | 无托管工具 | — | ❌ 明确提示"当前模型不支持联网" |

实现要点：

- `server/shared/llm.mjs` 的 `buildBody()` 增加可选 `tools` 参数，只有显式传入才写进 body；
- `streamChat()` 不动：`deepseek_web_search` 的检索在服务端完成，正文与引用走 `delta.content`；`server_tool_calls` 等字段忽略即可；
- 能力判定放在 `server/index.mjs handleAsk()`，用 `cfg.provider` + `cfg.model` 决定；不支持时给前端发一条 SSE `notice`（沿用现有 notice 类型），说明"当前模型不支持联网，已用论文内容回答"；
- **默认开**由前端 localStorage 控制（`paperlens.askWeb`，默认 `'1'`），服务端只被动接收 `webSearch`。

### 5.3 数据库

**无变更。** `ask_json` 仍存 `{role, text, quote}`；新增的 `askThread`/`structure` 字段只在请求体里流动，不单独落库。`structure` 已在 `papers.structure_json` 中，`askThread` 已在 `ask_json` 中，前端本来就有。

## 8. 验收点

1. `npm run check`、`npm run smoke` 全过；
2. demo 模式（无 Key）：追问仍返回 `DEMO_ASK`，无异常；
3. 真实模型：先问"核心方法是什么"，再问"它和 Transformer 比呢"——第二问的上下文里应出现上一轮问题和 `[§核心方法]`；
4. 选中 PDF 某段后问"这段在说什么"——上下文首位是 `[选中片段]`，且正文段落在该段附近；
5. 回答中出现 `[§…]` 角标，点击/复制后能对应到精读卡片；
6. 长论文（>5 万字）追问请求体不再带 12000 字正文，上下文总长 ≤7000 字符；
7. 无精读笔记时（新建论文直接追问）：退化为「标题 + 选中片段 + 正文 top-2」，不报错；
8. 连续追问 20 轮：请求里只带最近 6 条，回答不引用已淘汰的旧轮次；
9. **联网默认开**：DeepSeek 预设下问"这篇论文的方法现在有哪些后续改进"，请求体含 `tools:[{type:'deepseek_web_search'}]`，回答里网络结论带 `[网络]`；
10. **联网可关**：关掉开关后请求体不含 `tools`，回答只依据论文；刷新页面开关状态保持；
11. **不支持的模型**：切到 Ollama / Kimi 且开关开启时，前端收到 `notice`，显示"当前模型不支持联网"，回答仍基于论文，无异常。

## 9. 风险与降级

| 风险 | 处理 |
| --- | --- |
| 中文 bigram 召回噪声（如"方法"命中大量节） | 标题命中加权；长度归一；最多取 3 节 |
| 模型不输出来源标记 | system 强约束；前端不渲染也不影响正文可读性 |
| 历史回答本身有错，被当作上下文 | 历史只作为检索增强和背景，**不作为事实依据**；system 明确"依据带标记材料" |
| 问题与论文完全无关（如"今天天气"） | 检索全 0 时走兜底三节；联网开启时由模型判断是否搜索，system 禁止编造 |
| `structure` 为 null（精读后结构化失败） | `buildAskContext()` 里跳过 concepts/claims 加权，不影响主流程 |
| 联网工具增加延迟与 token 成本 | 默认开但用户可关；只注入托管工具、不自建循环；响应里工具事件不转发前端 |
| 服务商联网工具返回 `server_tool_calls` 等非正文结构 | `streamChat()` 忽略未知字段，只取 `delta.content` / `reasoning_content` |
| 网络信息与论文冲突 | system 要求两类来源分别标注，不混为一谈；论文事实优先 |
