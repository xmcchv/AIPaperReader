# 交互图解与概念定位：升级分析

> 状态：全部实施完成（2026-11-26），含规则+LLM 混合章节解析、前端目录、三向联动、PDF 词级高亮；测试全过
> 日期：2026-11-26
> 目的：为「交互图解设计升级」和「概念→原文定位升级」理清问题与可选方向

---

## 1. 一句话判断

**两个问题有同一个根因：`structure` 数据里没有"原文锚点"。**

图解节点、概念卡、追问上下文三处都从同一份 `structure` 取数据，但没有任何字段告诉它们"这个概念/节点对应原文的哪一段哪一句"。于是每处各自用运行时字符串猜测，三套算法互不相通。图解升不动级、定位不准，都是这个缺口的下游症状。

---

## 2. 现状盘点（代码可验证）

### 2.1 数据流

```
LLM 生成 structure（concepts / claims / diagram）
   ├→ 交互图解：diagram.render(data.diagram)，自研 SVG，最长路径分层
   ├→ 概念卡：conceptTerms() → data-terms → locateTerm() 字面正则
   └→ 追问：context.mjs tokenize() → 2-gram 加权选段落
三者之间没有连线，也没有指向原文的锚点。
```

### 2.2 图解侧的关键事实

| 项 | 现状 |
| --- | --- |
| 渲染 | `public/diagram.js` 541 行，原生 SVG 零依赖；自研「最长路径分层 + 层内顺序排布」 |
| 节点数据 | `id / label / detail / kind`，kind 仅 `input / process / data / output` 四种 |
| 交互 | 滚轮缩放、拖节点、拖画布、点击高亮一跳邻居、popover 看 detail、适应、导出 SVG、全屏 |
| 详情 | `showPopover()` 就地浮层，**不是可驻留面板**；detail 是唯一内容 |
| 对外 API | 仅 `{ render, fit, relayout, exportSvg }`；`highlight(id)` 是闭包私有，**外部无法驱动** |
| 与概念卡联动 | **无**。概念卡点击只定位原文，不会高亮图解节点；节点也没有 `conceptRef` |
| 布局短板 | 无交叉最小化、无节点大小感知的边路由；回边靠固定像素绕行；14 节点/30 边上限与提示词要求的 4–9 节点不一致，越界节点被静默丢弃可能断链 |
| 现成出口 | `server/kg/extract.mjs` 已把 diagram 映射为知识图谱的 `method` 节点 + `flow` 边 |

### 2.3 定位侧的关键事实

| 项 | 现状 |
| --- | --- |
| 检索词来源 | LLM 生成的 `concepts[].terms`，要求"原文逐字出现"；中文名/explain 括号内容兜底 |
| 文本定位 | `findTerm()`：空格/连字符拆段 + `[\s\-‐‑]*` 连接 + `i` 标志；**无词边界**，子串匹配 |
| PDF 定位 | `pdfView.locate()`：同样的正则；命中 `para.text` 后滚动 + 整段 flash + 弹卡片，**非词级高亮** |
| 选择策略 | terms 顺序 × 段落顺序双重循环，**第一个命中即停**；不打分、不排序、不留多候选 |
| 三套算法 | 前端 `findTerm`、`pdfView.locate`、`locateQuoteInText` 与服务端 `context.mjs` 的 2-gram 加权**完全不通源** |
| 明显失效场景 | 短缩写误命中（`RL` → `CTRL`）、跨段术语漏检、术语被 PDF 抽取切散、热区未渲染时静默跳过、中文名对英文论文无效、图谱回跳在 PDF 视图下静默失败、`<mark>` 定位后常驻 |

## 3. 升级方向

### 方向 A：先补「锚点」数据（推荐，是其它一切的前提）

在 `structure` 生成阶段，服务端把每个 concept 的 terms 在原文里跑一遍打分，选出最佳命中并附带：

```js
concept.anchors = [
  { paragraph: 12, offset: 340, quote: "…原文句子…", score: 0.82, source: "text" },
  { paragraph: 18, offset: 902, quote: "…", score: 0.61, source: "text" },
]
```

- 打分复用 `context.mjs` 已有的 `tokenize`/`scoreParagraph`，**不增加 LLM 输出负担**；
- 前端定位从"运行时猜"变成"按 anchor 直接跳"，失败再用现有正则兜底；
- 同一个 anchor 可同时供概念卡、图解节点、追问引用使用；
- PDF 视图通过 `para.text` 匹配 anchor.quote 落到对应热区。

**代价**：要在 structure 响应里增加字段、改 `normalizeStructure`、`context.mjs` 抽出共享打分函数。

### 方向 B：图解从「流程图」升级为「可钻取的知识视图」

分三层，层层递进：

1. **数据关联**：给 `diagram.nodes[]` 加 `conceptRef`（关联 concept name）和 `anchorRef`（指向 concept.anchor）。数据结构支持双向钻取，这是现在的硬缺口。
2. **对外 API**：把 `highlight(id)` 导出，形成三向联动——
   - 点概念卡 → 高亮图解节点 + 定位原文（当前只做后者）
   - 点节点 → 高亮概念卡 + 显示对应原文句子 + 「针对这步追问」按钮
   - 精读卡片/追问引用 → 反向定位到节点
3. **详情面板化**：popover 换成可驻留的侧边 detail 区（图解栏内分栏），容纳 detail + 原文引用 + 相关概念 + 追问入口。浮层适合"看一眼"，面板适合"读一段"。

**优先级**：1 和 2 是功能闭环，3 是体验优化。

### 方向 C：定位质量本身升级

不依赖锚点的独立改进，可与 A 并行：

- **词边界**：英文 term 加 `\b`；按 term 特异性排序（长词/少见词优先，缩写 `RL` 排最后）；
- **多候选**：不再"第一命中即停"，给出命中列表（段落预览 + 匹配度）让用户选；
- **跨段滑窗**：把相邻 `<p>` 拼接成滑窗再匹配，解决术语断在段落交界；
- **词级高亮**：文本侧用 `Range` API 做跨节点精确高亮；PDF 侧利用 `para.rects` 已有坐标画词级矩形；
- **交互细节**：定时清除 `<mark>`；toast 列出所有失败 term 而非只报 `terms[0]`；图谱 quote 回跳在 PDF 视图下改为切视图后重试。

### 方向 D：布局与可视化升级（锦上添花）

- 交叉最小化（重心排序）让边更少交叉；
- 边路由避让节点，回边不再固定像素绕行；
- 多视图切换：方法链路（现有横向分层）、阶段泳道、概念依赖网；
- 对齐提示词与后端上限（4–9 节点 vs 14/30 截断），避免静默丢节点。

---

## 4. 我的推荐组合

**先做 A + B1/B2，再做 C，最后 D。**

理由：
- A 是根，一次投入同时改善定位精度和图解联动的数据基础；
- B1/B2 把"三个孤岛"连成闭环，这是用户能直接感知的升级——点一个概念，图解、原文、追问同时响应；
- C 是兜底和体验，锚点命中失败时仍要有体面的降级；
- D 不改变信息结构，放在最后。

具体第一阶段（建议范围）：

1. `server/index.mjs` 的 `normalizeStructure()` 为 concept 计算 anchors，复用 `context.mjs` 的打分；
2. `diagram.js` 导出 `highlight(id)` / `clearHighlight()`；
3. `concept-list` 点击 → `diagram.highlight` + `locateTerm`（优先用 anchor）；
4. 提示词要求 `diagram.nodes[].conceptRef` 填 concept name，后端归一化校验；
5. `diagram.js` 节点点击 → 回调到 app.js → 高亮对应概念卡 + 显示 anchor.quote。

## 4.5 补充：先解析章节结构（混合方案）

用户提出一个更根本的判断：**论文应该先解析成章节结构，再谈 structure**。当前 `isSectionTitle()` 虽能识别章节标题，但结果只是给 `<p>` 加了个 CSS class，没有任何下游消费；精读的 7 小节是"解读模板"而非论文原始结构；structure/concepts/diagram 里没有任何字段指向"出自第几节"。章节是天然的锚点坐标系，补上它，锚点、图解关联、跨面板联动都会自然落地。

### 混合策略（采用）

| 层 | 职责 | 不做什么 |
| --- | --- | --- |
| **规则层**（纯函数，零成本） | 切段落 → 识别标题候选 → 建立编号/层级 → 算出每段属于哪节（`start/end` 段落索引） | 不生成小结、不猜测语义层级 |
| **LLM 整理层**（可选，一次轻量调用） | 只接收规则层给出的标题候选列表，判断层级归属、规范化标题、为每节写一句话小结 | **不做段落计数**——LLM 数不准第几段 |

关键设计：**LLM 不碰段落索引**。规则层给每个标题候选一个稳定 id（`h0, h1, …`），LLM 返回 `{ id, level, title, summary }`，规则层据此把小结映射回已有的段落区间。这样即使 LLM 输出有偏差，也不会破坏锚点坐标。

### outline 数据结构

```js
outline = {
  sections: [
    { id: 's1', number: '1', title: 'Introduction', level: 1,
      start: 0, end: 12,            // 段落索引区间（含 start 不含 end）
      headingIndex: 0,              // 标题所在段落
      summary: '...',               // LLM 生成，规则层为 '' 
      children: [] },               // level 2 的子节 id
  ],
  sectionOf: [0, 0, 0, 1, 1, ...],  // 段→节 的映射，长度 = 段落数
  source: 'rules' | 'hybrid',       // 是否经过 LLM 整理
}
```

### 与现有模块的关系

- 复用 `text.js` 的 `splitParagraphs()` / `isSectionTitle()` / `SECTION_RE` 及其抗噪规则（排除表格行、年份开头、折行脚注、长英文句）；
- 规则层放服务端 `server/paper/outline.mjs`，纯函数便于单测；
- LLM 提示词放 `server/prompts.mjs` 的 `outlineMessages()`；
- 无 API Key / demo 模式 → 只用规则层（`source:'rules'`），功能不缺失；
- 产出挂在论文记录上（`outline_json` 列，走已有缺列补列迁移），与 structure 分开——章节属于原文，structure 属于解读。

### 分阶段落地

1. **本轮（已完成）**：规则层 + LLM 整理层 + 混合入口 `parseOutline(cfg, text)`，配单测与真实论文验证；
2. **下一步（已完成）**：前端渲染目录树、段落标注 `data-section`；精读小节标注依据章节尚未做；
3. **再下一步（已完成）**：concept.anchors / diagram node.sectionRef / 追问按章节选段，全部改用 outline 坐标系。

**用户实测反馈修复（2026-11-26 晚）**：

1. **PDF 黄框形状错误**：原 `termRectFor` 把段落整体 rect 当成一行，导致高亮框 y 覆盖整段、x 只有词宽 → 画出贯穿整段的竖条。修复：用段落行高 `fh` 把 rect 切成多行，按字符比例定位命中行，高亮 y 只取该行（`y1 = y0 + fh`）。验证：80 单位高的 rect 现在高亮仅 12 单位（一行）。
2. **概念定位到 Abstract 而非 System Overview**：原打分把"靠前"当加分，摘要顺带提及得分最高。修复 `conceptAnchors` 打分：摘要/引言章节权重 0.35、overview/system/method/框架类 1.5；去掉 earlyBonus；加定义句加权 `DEFINE_RE`（we propose / is defined as / refers to / 定义为…）+0.9。验证：模拟用户论文（Abstract + System Overview），`state space layer` 定位到 System Overview（3.15 分）而非 Abstract（0.74）。

**解析章节按钮无反应（用户真实论文 SCAN-Planner）修复**：

根因链：
1. 用户库里 PDF 论文的 `papers.text` 全为 0（正文在 PDF/blocks 里），`loadOutline()` 开头 `if (!state.paper.text) return` 直接返回；
2. `loadOutline` 失败/0 节时静默无反馈；
3. **最关键**：论文用罗马数字章节（`I. Introduction` / `II. Related Work` / `VII. Conclusion`），`SECTION_RE` 只认阿拉伯数字，规则层解析出 0 节。

修复：
- `paperTextForOutline()` 统一取正文：`state.paper.text` 优先，空则 fallback 到 `pdfView.getText()`（复用精读/PDF 已抽好的结果），并回写 state；按钮显示条件也改用它；
- `loadOutline()` 对无正文/0 节/异常都 toast 明确反馈，不再静默；
- `text.js` 的 `SECTION_RE` / `isSectionTitle` 加罗马数字分支（`[IVXLCDM]{1,5}\.` + 大写字母/中文），排除单字母子节（A./C.）误判；`outline.mjs` 的 `parseNumber` 同步支持罗马数字。

实测：用户真实论文 SCAN-Planner 解析出 11 节（I Introduction / II Related Work / III System Overview / IV Yaw-Aware Local Planning / V 3D Sliding Map / VI Experimental Results / VII Conclusion 等）；浏览器点「目录」正常展开/收起，精读卡 §章节标注同步。截图 `docs/ui-preview/real-paper-outline.png`。`test:outline` 扩到 24 条（+罗马数字/+子节排除）。全测试通过。

**章节跳转改为跳 PDF 原版页（用户要求）**：

- `pdfview.js` 新增导出 `normalizeHeading()` / `headingMatchScore()`：章节号 + 标题匹配 PDF 段落，编号一致 +8、标题相等 +10/包含 +5、短标题 +2；**不再硬性要求 para.heading**——实测 SCAN-Planner 的 69 个 block 里只有「VII. Conclusion」是 heading，其余章节标题都是 `kind:body`；正文顺带提到章节名得分 <8 被阈值挡住。
- `pdfview.locateSection(number, title)`：只在像标题的段落里找最高分，滚到 `.pdf-para[data-pid]` 热区并 flash，返回 `{page,id}`，不弹卡片。
- `app.js jumpToSection()` 重写：有 PDF 就 `switchPaperView('pdf')` → await mount → `locateSection()`；失败才退回文本视图。
- 修 `normalizeHeading` / `parseNumber` 的编号剥除：不能把 "3D Sliding Map" 的 "3D" 当编号；罗马数字后跟空格即可（"V. 3D" 后面是数字）。

## 6. 风险与注意

- 增加 anchors 会让 `structure_json` 变大；论文级存储已有 `usage_json` 先例，可接受，但要在 `fitBudget` 和导出报告里注意体积。
- PDF 的 `paper.text` 与 PDF 抽取文本可能不完全一致，anchor 的 `paragraph` 索引以 `paper.text` 的 `splitParagraphs()` 为准，PDF 侧必须按 quote 文本反查，不能直接用索引。
- `conceptRef` 依赖 LLM 填对；后端要做校验，填错时退化为"无关联"，不能让图解渲染报错。
- 任何会触发 `schedulePaperSave()` 的调用前，必须先恢复所有会被 payload 读取的 state 字段（见 usage 丢失 bug 的教训）。
