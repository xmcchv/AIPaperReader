# 开发纪要

记录这个项目怎么一步步长出来的：**需求 → 决策 → 实测数据 → 踩过的坑 → 数据事故与防复发**。

- `README.md` 面向使用者：怎么启动、怎么用、接口有哪些。
- 这份面向维护者：为什么这么设计、哪些方案被否掉了、哪些数字是实测的、哪里不能碰。

最后更新：2026-10-30（对应版本 v3：多图谱）

## 1. 起点

参考站点：<https://47pn73utmp4d4.kimi.site>。要落地的四件事：

1. 论文、网页链接、图片都能变成**知识库里的资料**
2. 概念节点 + **前置关系**要清楚（"学这个之前得先会什么"）
3. 布局**稳定**：刷新、重开、换机器都不跳
4. 一键生成**思维导图**
5. 和 PaperLens（另一个项目，精读工具）的**精读输出联动**

### 形态选择

| 方案 | 结论 |
| --- | --- |
| **独立零依赖 Node 服务（:5180）+ 原生 HTML/CSS/ESM** | ✅ 选它。与 PaperLens（:5173）通过 HTTP 契约联动，互不打包、互不依赖 |
| 做成 PaperLens 的一个页面 | ❌ 耦合太深，图谱是长期资产，不该绑在精读工具的生命周期上 |
| 纯前端 localStorage / IndexedDB | ❌ 全文检索、多文献、快照都做不动 |
| 3D 力导向图 | ❌ 排除。可读性差、布局不确定，与"布局稳定"直接冲突 |

### 图谱视图

- **2D 分层有向图**：最长路径分层 + 同层重心排序，确定性输出（同样数据永远同样布局）
- 用户拖拽的偏移按 `mode + conceptId` 落盘（`layout` 表），重叠时仍以算法结果兜底
- **思维导图**：以选中节点为根的放射树，半径按"最小角距反推"算，避免节点重叠
- 导出 SVG / PNG（前端矢量序列化，不依赖服务端渲染）

## 2. 存储：从一个大 JSON 迁到 SQLite

第一版把整库塞进 `data/library.json`，每次改动全量重写。问题是**写放大**：500 份资料时，拖一下节点也要重写 10 MB。

所以迁到 `node:sqlite`（Node 自带，仍然零依赖）。同一台机器实测（100 份 × 2 万字）：

| 场景 | 旧版（JSON 全量重写） | 现在（SQLite 增量写） |
| --- | --- | --- |
| 导入 1 份资料后落盘 | 15 ms（库到 500 份时 90 ms） | **0.1 ms** |
| 拖动 1 个节点保存位置 | 15 ms | **~0 ms** |
| 冷启动加载整库 | 26 ms（500 份时 124 ms） | 1~7 ms |
| 写一半崩掉 | 靠 tmp + rename 兜 | **事务 + WAL，不会半写** |
| 概念重名 | 应用层判重 | `name_key` 唯一约束 |

顺带拿到的好处：外键级联（删资料自动清 `concept_sources` / `refs`）、每日快照可以用 `VACUUM INTO` 一条命令做。

代价：`engines.node >= 22.5`（`node:sqlite` 的门槛）。这个代价接受了——项目本来就是零依赖，不需要 npm install。

## 3. 全文检索：默认 LIKE，FTS5 只是可选加速器

这是被实测推翻过一次的决策。

**第一直觉**：上 FTS5。实际踩下来：

| 分词器 / 方案 | 实测结论 |
| --- | --- |
| FTS5 `unicode61`（默认） | 中文 **0 命中**（它按空格切词，中文整句是一个 token） |
| FTS5 `trigram` | 能用，但**要求查询 ≥ 3 字符**，"注意""稀疏"这种 2 字查询直接失效 |
| FTS5 `trigram` 成本 | 500 份 × 2 万字：索引 **50.9 MB**（正文 10 MB）、灌库 **9.7 s** |
| FTS5 `trigram` 高频词 | "模型"这类词反而 **80 ms**（索引里命中太多，回表爆炸） |
| **SQLite `LIKE` 全表扫描** | 最坏 **36 ms**（同样 500 份 × 2 万字），2 字中文天然支持 |

**结论**：`LIKE` 做默认路径；FTS5 保留为**可选加速器**（设置里开关，或 `KGRAPH_FTS=1`），只在关键词稀疏、库很大的时候快（0.6 ms）。

实现上的两个坑：

- `detail=none` 的 FTS 表不支持 phrase 查询，裸查询里出现 `O(n log n)` 这种字符会直接语法错误 → 查询必须**整体转成 phrase 并转义双引号**
- 正确性不依赖索引：FTS 粗筛无果时**自动回退 LIKE**，所以打开 FTS 永远不会"搜不到"

## 4. 多图谱（工作区）

### 问题

所有文献都进同一个库 → 语义分割的论文和 SLAM 的论文互相连边，59 个实体 + 68 个待补全挤在一张图上，读不了。

### 方案对比

| 方案 | 结论 |
| --- | --- |
| **一图一库**：`data/graphs/<graphId>.db`，每个图谱一个独立 SQLite 文件 | ✅ 选它 |
| 所有表加 `graph_id` 列 | ❌ 隔离不彻底；`UNIQUE(name_key)` / `UNIQUE(from,to,type)` 全部要改成联合唯一；删图谱要写一大段级联清理；查询处处要带过滤 |

一图一库的收益：**隔离是文件级的**（不可能串数据）、删图谱 = 删一个文件、迁移简单（旧库 `VACUUM INTO` 直接搬进来）、schema 一个字都不用改。

### 数据布局

```
data/graphs/<graphId>.db              一个图谱的全部数据（meta/sources/concepts/...）
data/graphs/active.txt                上次打开的图谱 id
data/backups/<graphId>-YYYY-MM-DD.db  每个图谱的每日快照（各留 7 份，按 graphId 前缀轮转）
data/assets/                          图片素材（跨图谱共享）
```

- 图谱 id 形如 `g_605023bc`，`/^g_[A-Za-z0-9]{3,32}$/`，有校验，防止路径穿越
- 每个库的 `meta` 表里存 `graph_name` / `graph_description` / `graph_created_at`
- 空图谱会自动补一个默认名「我的知识库」

### 迁移（两段，都自动）

| 从 | 到 | 做法 |
| --- | --- | --- |
| `data/library.json`（最早版本） | 当前图谱 | `migrateLegacyJson()`：迁入后把原文件改名成 `library.legacy-<时间戳>.json` **留档，不删除** |
| `data/library.db`（v2 单库） | `data/graphs/g_xxxx.db` | `VACUUM INTO` 复制 + 写 meta + 删除旧库三件套（`.db` / `-wal` / `-shm`） |

实测：v2 的 4 资料 / 127 概念 / 231 关系完整迁入，二次启动不重复迁移，启动日志会打出当前图谱指纹。

### 接口

```
GET  /api/graphs              列表（含每个图的资料/概念/关系数与说明）
POST /api/graphs/create       新建并切过去 {name, description}
POST /api/graphs/rename       改名/改说明 {id, name, description}
POST /api/graphs/delete       删除（快照保留）
POST /api/graphs/activate     切换当前图谱 {id}
```

其余所有 `/api/*` 都接受 `?graph=<graphId>`：服务端在处理请求前 `activateGraph()`，**不带就用当前激活的那个**。这样 PaperLens 那种"不带参数"的老调用方零改动就能继续工作。

`?graph=` 传了无效 id 时不报错、静默回退当前图谱——一个 URL 参数不该让整个请求 500。

### 前端

- 顶栏「我的知识库 ▾」是切换器，点开是管理对话框：列表（名称 + 计数 + 说明）、新建、`✎` 改名、`✕` 删除
- `api()` 统一在 path 上追加 `graph=<state.graphId>`；`activate` 这类请求显式传空串表示"这次不带图谱"
- 切换图谱会重置选中状态、搜索框、资料筛选，然后重新 `fit()`
- URL 支持：`?graph=<id>` 直接开某个图谱，`?source=<id>` 直接进"只看这篇"

### 单个图谱内部的降噪

多图谱解决"跨主题混杂"，但**一个图谱里塞了 4 篇论文**依然很密。所以补了两个视图过滤（都不动数据）：

| 手段 | 效果 | 状态存哪 |
| --- | --- | --- |
| 「只看这篇的图」（资料详情里，或 `?source=`） | 4 篇混排 127 节点 → 单篇 14 节点，80% 缩放可读 | 内存 `state.sourceFilter` |
| 「显示待补全」（工具栏开关） | 68 个 stub 默认隐藏，否则分层图被压成一列 | `localStorage` |

两个过滤叠加后才真正可读。图上的筛选胶囊点一下即可回到整张图。

## 5. 事故：误删 `data/`（必须记住的一条）

**经过**：多图谱改造收尾时，为了"清干净现场"，执行了 `Remove-Item -Recurse -Force data`。目录里有刚迁移出的库、`library.legacy-*.json` 留档、以及原始 `library.json`——**一起没了**。

**恢复尝试全部失败**：回收站无、卷影副本（VSS）不可用、全盘搜索无残留。

**补救**：从 `C:\Users\lcheng\Downloads` 找到 4 份 PaperLens 导出的「精读报告.html」，写了 `tools/restore-from-reports.mjs` 重新灌库 → 4 资料 / 127 概念（59 实体 + 68 待补全）/ 231 关系（prereq 171、flow 39、related 12），31 个概念带出处。

**有损的部分**：出处来自报告正文而不是论文原文；第 5 份资料没有报告，永久丢失；图片素材与追问记录丢失。

**防复发（三条，长期有效）**：

1. **绝不删除 `data/` 目录**。清理现场只清 `.probe/` 这类临时目录，`data/` 一律不碰。
2. **每日快照**：每个图谱每天第一次打开时 `VACUUM INTO` 一份到 `data/backups/`，各留 7 份。空图谱不生成。
3. **恢复工具常驻**：`tools/restore-from-reports.mjs --dir=<目录> [--import]` 能从精读报告把概念与链路图重新灌回去。

## 6. 踩过的坑

| 现象 | 原因 | 修法 |
| --- | --- | --- |
| 画布全空 | `<svg viewBox="0 0 100 100">` 把所有坐标当成"100 单位坐标系" | 移除 viewBox，改用显式 `width/height` + transform |
| 箭头不可见 | 把 CSS 变量写在 SVG presentation attribute 上（无效） | 改用 `.arrow-head-*` class 承载 `fill` |
| 名字被乱切（`Transfo` / `rmer 编…`） | 按字符数切行，中英混排宽度差一倍 | `splitLabel` 改按**显示宽度**估（中文 2、英文 1），`LINE_UNITS=13` |
| 待补全节点仍然渲染 | `init()` 走了 `state.library` 而没走 `visibleLibrary()` | 统一入口：`applyLibrary` / `applyStatePayload` 都过 `visibleLibrary()` |
| 空图显示 78% | `fit()` 对零尺寸内容做了缩放计算 | 空图固定 `k=1` |
| 改了代码但行为没变 | 后台 node 进程 kill 不掉，端口被旧进程占着 | `Get-NetTCPConnection -LocalPort 5180` 找 PID + `Stop-Process -Force` |
| 用 `Invoke-RestMethod` 发中文 JSON 变乱码 | PowerShell 默认编码 | 用 node 脚本发请求，不用 `Invoke-RestMethod` |
| `write_file` 写 `$env:TEMP` 后 node 读不到 | 沙箱里 `$env:TEMP` 指向别处 | 临时文件统一放仓库内的 `.probe/`（已 gitignore） |

## 7. 当前状态

**数据**：1 个图谱「我的知识库」，4 份资料 / 127 个知识点（59 实体 + 68 待补全）/ 231 条关系，库文件 `data/graphs/g_605023bc.db`（约 224 KB）。

**代码规模**：

```
server/store.mjs    ~51 KB   SQLite 存储 + 多图谱 + 迁移 + 快照 + 检索
server/index.mjs    ~28 KB   零依赖 HTTP 服务 + 路由 + LLM 抽取编排
server/extract.mjs  ~14 KB   抽取 / 前置补全 / PaperLens 适配 / 图片描述
public/graph.js     ~36 KB   布局算法 + 渲染 + 导出
public/app.js       ~60 KB   状态机 + 三栏 UI + 对话框
tools/restore-from-reports.mjs  从精读报告还原
```

**验证方式**（没有测试框架；脚本都是一次性的，跑完即清理，不进仓库）：

- `node --check` 全部源码（每次改完必跑）
- SQLite 回归脚本：示例幂等、CRUD、唯一约束、级联删除、导出→清空→恢复、压力写入（40+ 项）
- 多图谱回归脚本：新建/切换/重命名/删除、**概念与检索与布局的跨图隔离**、无效 `?graph=` 回退、空名兜底、导出取当前图谱（20 项）
- headless Chrome 截图核对：空态、分层图、思维导图、搜索高亮、资料筛选后视图
- 基准脚本：JSON vs SQLite 写入、LIKE vs FTS5 检索

改存储层时建议按同样的清单再跑一遍——尤其"跨图谱隔离"那几项，串数据是这类改动最容易出的错。

**已知边界**：

- 只监听 `127.0.0.1`，不做鉴权，假设单人本机使用
- 抽取依赖外部 LLM（DeepSeek），失败时只落资料不落概念，需要手动重抽
- 出处（`refs`）定位到句子级，跨句引用会降级成整段
- 没有"把某份资料连同概念搬到另一个图谱"的功能：概念可能被多篇共享，跨库迁移有取舍，暂时用「只看这篇」代替
- 图片只做描述性抽取，不做 OCR

**可以继续做的**（按价值排序）：

1. 图谱内"按资料移动/拆分"（跨库迁移工具）
2. 概念合并（同一概念两种叫法）
3. 精读报告 → 图谱的增量更新（现在只支持全量灌入）
4. 时间线视图（哪个概念是哪天进来的）

## 8. 运维手册

```powershell
# 启动（默认 127.0.0.1:5180）
node server/index.mjs

# 换端口（数据仍用默认的 data/）
$env:PORT=5190; node server/index.mjs

# 换数据目录：那里会是一整套独立的图谱，和 data/ 互不影响
$env:KGRAPH_DATA_DIR='D:\kg-data'; node server/index.mjs

# 端口被占：找到占用的进程
Get-NetTCPConnection -LocalPort 5180 -State Listen | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
```

**还原某天的快照**（**先停服务**）：

```powershell
Copy-Item data\backups\g_605023bc-2026-10-30.db data\graphs\g_605023bc.db -Force
```

**从精读报告还原概念与关系**：

```powershell
node tools/restore-from-reports.mjs --dir="C:\Users\lcheng\Downloads"            # 只打印解析结果
node tools/restore-from-reports.mjs --dir="C:\Users\lcheng\Downloads" --import   # 真的写入当前图谱
```

**新建一个主题图谱**：顶栏切换器 → 填名字 → 新建。之后导入的资料只会落到这个图谱；PaperLens 推送同样落到当前激活的图谱。

## 9. 合并后的变化（v2.0）

原来的「论文精读」与「知识图谱」现在是一个仓库、一个进程、一个端口：

- **启动**：`node server/index.mjs` → `http://127.0.0.1:5173`。图谱不再单独监听 5180；旧地址 `/kg/` 会 302 到 `/?view=kg`。
- **单页外壳**：`/` 同时承载精读与图谱，左上角 `精读 | 知识图谱` 开关切换，`?view=kg` 记录状态。图谱的 CSS 已作用域化到 `.kg-view`、ID 加 `kg-` 前缀，两个状态机互不干扰。
- **共享配置**：`~/.paperlens/config.json` 同时保存文本模型与视觉模型；一次解锁两边都可用。旧 `~/.kgraph/config.json` 仅作只读回退。
- **数据目录**：从仓库内 `data/` 迁到 `~/.paperlens/data/`（`graphs/`、`backups/`、`assets/`、`papers/`、`papers.db`）。迁移是复制，原目录保留。
- **论文库**：新增 `papers.db`，正文 / 精读 / 结构化 / 追问 / PDF 都落盘；精读页自动保存，`?paper=<id>` 可恢复。
- **联动**：精读页「→ 知识图谱」进程内调用 `/api/kg/import/paper`，不再跨端口；图谱出处「回精读」优先带 `paperId` 与 `quote`，精读页会定位到该句。
- **代码位置**：共享模块在 `server/shared/`，精读路由仍由 `server/index.mjs` + `server/paper/` 承担，图谱在 `server/kg/`。

合并后的回归清单：

1. `node --check` 全部 `server/**/*.mjs` 与前端模块。
2. 一个进程同时打开两个视图；模型设置只填一次。
3. 示例论文 → 精读 → 推送图谱：概念、`flow` 边、原文出处齐全。
4. 图谱出处「回精读」→ 定位到 `?paper=&quote=`。
5. 刷新 / 重启 / 换浏览器：论文库与精读结果仍在，PDF 原版可回。
6. 多图谱切换：`?graph=` 不串库；旧别名 `/api/state`、`/api/import/paperlens` 仍可用。
